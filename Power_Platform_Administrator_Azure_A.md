# Power Platform Administrator & Azure Administrator — Interview Prep

Two sections below: Power Platform admin questions first, then Azure admin questions. Many orgs now screen for both together, since Power Platform governance increasingly touches Azure services (Key Vault, App Insights, Entra ID), so the overlap is worth leaning into if asked how the two connect.

---

## Power Platform Administrator

**1. What is a Power Platform environment, and how would you design an environment strategy for an enterprise?** An environment is a space that holds apps, flows, connections, and Dataverse data, with its own security boundary and settings. For an enterprise, I'd separate Development, Test/UAT, and Production, add a dedicated environment for the CoE Starter Kit and admin tooling, and use environment groups (a Managed Environments feature) to apply consistent rule-based policies instead of configuring each environment individually. I'd also restrict who can create new environments — uncontrolled self-service creation is one of the fastest ways governance breaks down as a tenant grows.

**2. What's the difference between a Managed Environment and a regular environment, and when would you enable it?** Managed Environments is a licensed, premium layer of governance features you turn on per environment — solution checker enforcement, weekly digest emails to admins, sharing limits on canvas apps, IP firewall rules, customer-managed keys, and extended backup retention, among others. I'd enable it first on anything touching production data or external users, since that's where sharing limits and solution-checker enforcement matter most, then expand tenant-wide as licensing allows.

**3. Walk me through how DLP policies work in Power Platform.** DLP policies classify connectors into groups — Business, Non-Business, and Blocked — and data can't flow between a Business connector and a Non-Business connector in the same flow or app. So if SharePoint is Business and a consumer social connector is Non-Business, you can't build a flow moving data between them. Policies can be scoped tenant-wide or per environment, and the first thing I'd lock down is the Default environment, since every licensed user holds the Environment Maker role there with no DLP policy applied out of the box.

**4. Why is the Default environment considered a governance risk?** Because every licensed user automatically gets Environment Maker rights in it, and Microsoft doesn't apply a DLP policy there by default. That means anyone can build and share an app or flow — potentially connecting a sensitive data source to a public connector — before IT knows it exists. The standard fix is applying a strict baseline DLP policy to Default on day one and steering real development into purpose-built, managed environments.

**5. What is the CoE Starter Kit, and what role does it play in governance?** It's a free, Microsoft-provided set of Power Platform apps, flows, and dashboards that gives admins a full inventory of every app, flow, and connector across the tenant, plus governance workflows like approval requests and usage/adoption analytics. It doesn't replace Managed Environments or DLP — it's the visibility and process layer on top, so you actually know what's being built and by whom before deciding where to tighten controls.

**6. How do you manage security within Dataverse?** Through security roles, business units, and teams. Security roles define what a user can do (create/read/write/delete, and at what access level), business units define ownership boundaries, and teams let you assign roles to groups rather than one user at a time. I'd default to least-privilege roles, use business units to mirror data-sensitivity boundaries rather than the org chart, and drive team membership from Entra ID security groups so access stays centrally managed.

**7. How does ALM work in Power Platform?** Solutions are the packaging mechanism — you build in an unmanaged solution in dev, then export/import a managed solution into test and production so downstream components can't be edited directly. Pipelines (a Managed Environment feature) move solutions between environments through a controlled, auditable process instead of manual export/import, and for more mature teams that's backed by source control (Azure DevOps or GitHub) with automated builds via the Power Platform CLI.

**8. How do you monitor and control licensing and capacity consumption across a tenant?** The admin center's Billing and Analytics views show license consumption and per-environment capacity — API calls, Dataverse storage — against what's provisioned. I'd run regular reviews of unlicensed or inactive users holding capacity, use the CoE kit's inventory to catch abandoned apps and flows, and track Dataverse storage trends per environment so a runaway flow or a bad data model doesn't quietly blow through capacity.

**9. What governance controls exist specifically for Copilot Studio and AI Builder?** DLP policies extend to AI-related connectors and can restrict which environments are even allowed to publish Copilot Studio agents. There are tenant-level settings for agent publishing and cross-tenant data access, AI Builder credit consumption is tracked per environment and tenant, and Managed Environments lets you require review before an agent goes live. This area moves fast, so I'd treat new AI connectors the way I treat any new connector — default to restrictive, then open up deliberately.

**10. How would you approach backup and disaster recovery for a Dataverse environment?** Dataverse takes automatic system backups on a rolling retention window (longer under Managed Environments), and you can trigger manual backups before risky changes like a major deployment or data migration. Recovery is a point-in-time restore, either into the same environment or a new one. I'd periodically test a restore into a fresh environment rather than assume the backup works, and keep solutions source-controlled so app and flow logic doesn't depend solely on the Dataverse backup.

## Azure Administrator

**1. Explain the Azure resource hierarchy and how RBAC scope fits into it.** It's Management Group → Subscription → Resource Group → Resource, and permissions assigned at any level inherit down to everything below it. A Contributor role assigned at the subscription level applies to every resource group and resource underneath unless overridden lower down. I assign RBAC at the narrowest scope that's still operationally sensible — a developer gets Contributor on the Dev resource group, not the whole subscription — since overly broad scope is one of the most common ways over-privileged access creeps in.

**2. What's the difference between Azure RBAC and Azure Policy?** RBAC controls who can do what — it's about identity and permissions. Policy controls what resources are allowed to look like or do, regardless of who's deploying them — things like "only allow VMs in these regions" or "require a cost-center tag on every resource group." I use them together: RBAC gates who can create things, Policy enforces standards on what gets created even by people who do have permission.

**3. Walk me through the storage redundancy options and when you'd choose each.** LRS (locally redundant) keeps three copies in a single datacenter — cheapest, but no protection if that datacenter goes down. ZRS (zone-redundant) spreads copies across availability zones in the same region, protecting against a datacenter-level failure. GRS (geo-redundant) replicates asynchronously to a paired region for disaster recovery, and RA-GRS adds read access to that secondary region's copy. For anything business-critical I'd default to GRS or RA-GRS; for dev/test or easily-reproducible data, LRS is usually fine and cheaper.

**4. How does NSG rule evaluation work, and how would you troubleshoot a connectivity failure?** NSG rules are evaluated in priority order, lowest number first, and evaluation stops at the first match — there's no special precedence for deny over allow, priority alone decides it. For troubleshooting, I'd check both the subnet-level and NIC-level NSG since both can apply, review effective routes and effective security rules for the NIC (Azure shows the computed result directly), and use Network Watcher's IP flow verify or connection troubleshoot tools rather than guessing — a lot of "NSG problems" turn out to be a route table sending traffic somewhere unexpected.

**5. What's the difference between Azure Load Balancer and Application Gateway?** Load Balancer operates at Layer 4 — it distributes TCP/UDP traffic by IP and port and doesn't inspect the actual HTTP request. Application Gateway is Layer 7, so it handles path-based routing, SSL termination, and cookie-based session affinity, and it has an integrated web application firewall. If I just need to spread traffic across VMs, Load Balancer is simpler and cheaper; if I need URL-based routing or WAF protection for a web app, that's Application Gateway.

**6. When would you use VNet peering vs. a VPN Gateway vs. ExpressRoute?** Peering connects two Azure VNets directly over Microsoft's backbone — fast, no gateway required, but Azure-to-Azure only. A VPN Gateway connects an on-premises network (or another cloud) to Azure over the public internet through an encrypted tunnel — good for smaller sites or as a backup path. ExpressRoute is a private, dedicated circuit to Azure that never touches the public internet, used when you need consistent low latency and higher bandwidth, typically as the primary connection for an enterprise datacenter.

**7. What's the difference between an Availability Set and an Availability Zone?** An Availability Set spreads VMs across multiple fault domains and update domains within a single datacenter, protecting against a rack-level hardware failure or planned maintenance. Availability Zones go further — they're physically separate datacenters within a region, each with independent power and networking, protecting against an entire datacenter going down. Zones give a stronger SLA, but not every region supports them, so that's a design constraint to check early.

**8. How do you approach backup and disaster recovery in Azure?** For backup, Recovery Services Vault handles scheduled, policy-based backup for VMs, SQL, and file shares, with configurable retention. For disaster recovery — keeping a workload running if an entire region goes down — that's Azure Site Recovery, which replicates VMs to a secondary region and supports failover on demand or automatically. I'd define an RPO/RTO target with the business first, since that decision drives whether simple backups are enough or you need full cross-region replication.

**9. Walk me through setting up monitoring and alerting for a production workload.** I'd route diagnostic logs and metrics from the relevant resources into a Log Analytics workspace, build KQL queries or use built-in Azure Monitor metrics for what actually matters — CPU/memory for VMs, response codes for App Service, DTU/CPU for SQL — and set alert rules tied to action groups so the right people get notified (email, SMS, or a webhook into a ticketing system) when thresholds are crossed. I'd also build an Azure Monitor dashboard or Workbook so the team has one view instead of hunting through separate resource blades.

**10. What is Microsoft Entra ID, and how does Entra Connect fit into a hybrid scenario?** Microsoft Entra ID (formerly Azure AD) is Microsoft's cloud identity and access management service — it authenticates users into Azure, Microsoft 365, and any app that trusts it. In a hybrid environment where the company still runs on-prem Active Directory, Entra Connect (previously Azure AD Connect) syncs identities from on-prem AD up to Entra ID so users have one identity across both, and it can enable password hash sync or pass-through authentication so IT isn't managing two separate credential stores.

## A few quick interview tips

- Both roles get asked **scenario questions**, not just definitions — expect "a developer needs access to only the Dev resource group, where do you assign the role?" rather than just "what is RBAC?" Practice narrating your reasoning out loud, not just naming the right answer.
- If asked how the two roles overlap, a good real answer: Power Platform admins increasingly rely on Azure Key Vault (for connector secrets), Application Insights (for monitoring custom Power Platform apps), and Entra ID (for security groups and Conditional Access) — so basic Azure admin fluency directly strengthens Power Platform governance.
- Have one real example ready per topic — even a lab environment you set up yourself counts, and it reads far better than a memorized definition.
